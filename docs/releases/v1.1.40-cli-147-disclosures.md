# v1.1.40 — CLI 1.4.7 wire pass: สอง disclosure ไม่เงียบอีกต่อไป

Previous: v1.1.39 · วันที่: 2026-10-14

## สรุปหนึ่งบรรทัด

Muse CLI อัปเดตเงียบเป็น `1.4.7-R6101.1` — รอบนี้ยืนยันว่าไม่มีอะไรพัง
(full-turn smoke 5/5) และรับ notification เปิดเผยสถานะสองตัวของ wire ใหม่
`view/gap` กับ `session/modelRouteUnserved` เข้ามาเป็นข้อความเตือนถาวรในแชท
แทนที่จะหล่นเป็น `agent_update_other` ที่ผู้ใช้ไม่เห็นอะไรเลย

## ที่มา / ปัญหาก่อนแก้

- ตัว launcher ดาวน์โหลด binary ใหม่ให้อัตโนมัติและ **ไม่มี changelog สาธารณะ**
  (channel API ส่ง `notification_text` ว่าง) — วิธีรู้ว่า wire เปลี่ยนหรือเปล่า
  คือ export schema จากตัว binary แล้ว diff กับค่าที่ desktop ปักหมุดไว้
- Desktop ปักหมุด wire ไว้หลายจุดจากยุค 1.4.2/1.4.3 (รหัส error ชุด settle,
  เพดานข้อความตอบ 500 ตัวอักษร, `reason` ที่ schema บอกว่า optional แต่
  binary บังคับ — เคส BUG-084) ต้องเช็กซ้ำทุกครั้งที่ binary ขยับ
- Schema 1.4.7 มี notification ที่ desktop ไม่มี handler อยู่ 14 ตัว —
  ทั้งหมดถูกส่งต่อเป็น `agent_update_other` (ไม่ถูกกลืน ตามกฎเดิม) แต่
  **ไม่มีอะไรปรากฏในแชท** สองตัวในนั้นมีผลกับผู้ใช้โดยตรง:
  - `view/gap` — ฝั่ง push ทำเหตุการณ์ช่วง `(after, next)` หาย: transcript
    ของ desktop จะขาดช่วงโดยไม่มีคำอธิบาย อ่านเหมือน agent ตอบข้ามเอง
  - `session/modelRouteUnserved` — หลังเปลี่ยนข้อมูลล็อกอิน โมเดลที่เลือกค้างไว้
    route ไม่ได้อีก (wire ไม่เปลี่ยน selection ให้) เทิร์นถัดไปจะล้มโดยไม่มี
    สาเหตุบันทึกไว้ที่ไหนในแชท

## กลไก

1. **msp-client** (`src/server/msp-client.js`): เพิ่ม case ระบุชื่อสองตัว —
   `view/gap` → `msp:viewGap {after, next}`,
   `session/modelRouteUnserved` → `msp:modelRouteUnserved {modelId, …}` —
   ส่วน notification อื่นยัง forward เป็น `msp:<method>` เหมือนเดิม
2. **sessions** (`src/server/sessions.js`): ทั้งสองชนิดลงเป็นข้อความ
   `role: 'notice'` ภาษาไทยที่ persist ลง store (รอดรีโหลด, แบบเดียวกับ
   notice ของ BUG-084) — gap เตือนว่า "คำตอบอาจขาดช่วง ส่วน agent ทำงานต่อ",
   unserved บอกชื่อโมเดลและให้เลือกโมเดลอื่น แล้ว broadcast
   `agent_update_other` ต่อเพื่อให้ trace ฝั่ง SSE ยังครบ ไม่แก้ renderer
   เพราะ notice เรนเดอร์ผ่านเส้นทางข้อความปกติอยู่แล้ว
3. **ApprovalMode** (`src/server/session-mode.js`): enum ของ 1.4.7 มีค่า
   ที่สี่ `onRequest` — map เป็น ask แบบ explicit (เดิมหล่นปลายฟังก์ชัน
   ได้ผลเดียวกันโดยบังเอิญ) กันเซสชันที่ TUI ตั้งโหมดนี้ไว้แสดงชิปเพี้ยน
4. **Version pins**: comment ที่อ้าง binary 1.4.2/1.4.3 ปรับเป็นฐาน 1.4.7
   โดยเก็บที่มาเดิมไว้ (เรื่อง `reason` ยังเป็นบทเรียน BUG-084 ไม่ใช่ของใหม่)
   และ AGENTS.md บันทึกข้อเท็จจริงสอง disclosure เพิ่ม

  fingerprint `sha256:6de32db08bbbe0deb478d2bfcaba001e9fb490986bc80db3aceb4d996abf7df9`,
  schemaVersion 1) เทียบทีละจุด: ทุก method ที่ desktop เรียกยังอยู่ครบ,
  รหัส -32050..-32057 ครบและ `retryable: false`, เพดาน 500 เท่าเดิม,
  `required` ของ `userInput/cancel` ยังไม่มี `reason` (binary บังคับอยู่ดี —
  fix เดิมยังจำเป็น), `contributor_mode_enabled` คีย์เดิม
- `scripts/smoke-msp.mjs` กับ binary สด: **5/5 แถวผ่าน** (default /
  reconnect / config / mode-plan / mode-always) — full turn จริงครบวงจร
- เทสใหม่แบบ RED→GREEN: msp-client 2 เคส (สอง disclosure map เป็น kind
  มีชื่อ + unknown ยัง forward), session-mode 1 เคส (enum ครบสี่ค่า),
  e2e เพิ่ม 1 step — mock ยิงสอง disclosure กลางเทิร์น (`viewgap`) แล้ว
  assert ว่า notice ทั้งสองถูก persist พร้อม meta: e2e **95/95**

## ที่ตั้งใจไม่ทำ

- **ไม่ทำ splice-fill** ตามที่ schema เสนอ (buffer + page ช่วงที่หายมาเติม):
  schema ระบุว่า server ไม่บังคับทั้งสองทาง และ desktop เก็บ transcript
  ของตัวเอง — แจ้งเตือนผู้ใช้ตรง ๆ ซื่อสัตย์กว่าการเย็บข้อความย้อนหลังเงียบ ๆ
- **ไม่ auto-repair โมเดล** หลัง unserved: การเดาโมเดลแทนผู้ใช้เสี่ยงกว่า
  การบอกให้เลือกใหม่เอง
- notification ที่เหลืออีก 12 ตัว (`session/nameChanged`, `skill/changed`,
  `plugin/changed` ฯลฯ) ยังถูก forward เป็น trace อย่างเดียว — ส่วนใหญ่
  เป็นสถานะที่ desktop เป็นเจ้าของเองอยู่แล้ว (รายชื่อแชท ชื่อ ชิปเอเจนต์)
