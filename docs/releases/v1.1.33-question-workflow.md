# v1.1.33 — ขั้นตอนคำถาม + แจ้งเตือนจาก host

> Previous: [v1.1.32](https://github.com/aukkwat83/muse-desktop-guix/blob/v1.1.32/docs/releases/v1.1.32-activity-overview-and-icons.md) ·
> วันที่: 2026-10-08 · base: `main@739172e`

รีลีสนี้ตอบคำถามผู้ใช้: **เมื่อ Muse มีคำถาม เดสก์ท็อปจะถามเราผ่านป๊อปอัปหรือไม่**
พฤติกรรมหลังรีลีสนี้: คำถามใหม่จะขึ้นเป็นการ์ดในแชทของมันเอง พร้อมป๊อปอัปกล่องคำถาม
(มีคิว ป้าย badge เปิดใหม่ได้) และบน Linux จะมีแบนเนอร์จาก host process
ที่แตะแล้วพาไปถึงแชทกับคำถามข้อนั้นตรงตัว การส่งคำตอบรอผลยืนยันจาก agent
ก่อนถือว่าเสร็จ และฉบับร่างคำตอบยังอยู่เมื่อปิด/เปิดกล่องใหม่ สลับแชท หรือโหลดหน้าใหม่

ลิงก์ไฟล์ทั้งหมดในโน้ตนี้ชี้แท็ก `v1.1.33` ของ repo นี้
(`https://github.com/aukkwat83/muse-desktop-guix`)
จึงอ่านโน้ตฉบับนี้เป็น GitHub Release body ได้โดยตรง

## 1. สิ่งที่ผู้ใช้เห็นเมื่อ Muse มีคำถาม

- คำถาม (`AskUserQuestion`) ขึ้นเป็นการ์ดในแชทที่เป็นเจ้าของคำถาม พร้อมป๊อปอัป
  "กล่องคำถาม" ภาษาไทย ป๊อปอัปมีคิวแบบถามก่อน-ตอบก่อน ถ้ามีหลายข้อจะต่อคิวกัน
  ([question-inbox.js](https://github.com/aukkwat83/muse-desktop-guix/blob/v1.1.33/src/renderer/question-inbox.js))
- คำถามจากแชทอื่น (background) ก็ขึ้นป๊อปอัปเช่นกัน โดยไม่ย้ายแชทที่กำลังอ่าน
  และไม่ขโมยโฟกัส/caret หรือทับกล่องโต้ตอบ overview/config ที่เปิดอยู่ —
  กรณีนั้นจะมี badge + แบนเนอร์รอให้เปิดเอง
- ปิดกล่องหรือกด Esc คือ "เลื่อนไปก่อน" ไม่ใช่ยกเลิก: เปิดใหม่ได้จาก badge
  ส่วน "ยกเลิกคำถาม" เป็นปุ่มแยกต่างหากที่ส่งการยกเลิกจริงไปยัง agent
- การ์ดขออนุญาต (permission/approval) ยังแยกจากคำถามผู้ใช้เหมือนเดิม
  และใช้เส้นทางส่งแบบเดียวกันโดยไม่ลดทอนเงื่อนไข policy

## 2. ฟอร์มคำถามตาม schema จริงของ binary

รูปแบบฟอร์มยึดตาม exported schema ของ `muse` ที่ติดตั้ง
(`muse schema generate-json-schema`) ไม่ได้เดา field เอง:

- คำถามเลือกข้อเดียว (`single`) เลือกหลายข้อ (`multi`) และคำถามพิมพ์ตอบ
- ทุกคำถาม choice มีแถว "อื่น ๆ (พิมพ์เอง)" เป็นทางเลือกอิสระตาม schema
  (ข้อความอิสระยาวได้ไม่เกิน 500 ตัวอักษร) พร้อมช่องโน้ตเพิ่มเติม
- `minSelections: 0` เลือกเว้นว่างได้จริง ระบบไม่บังคับเลือกขั้นต่ำเอง
- id/label ส่งตรงตัวอักษรทุกตัวรวมช่องว่างหน้า-หลัง (trim ฝั่ง client แล้ว agent จะ 400)
  และขอบเขต min/max ผ่านการ validate ไม่เขียนทับเงียบ
- คำตอบทุกข้อในคำถามเดียวส่งแบบ atomic: ข้อเดียวไม่ผ่านคือไม่ผ่านทั้งชุด
  พร้อมข้อความบอกว่าข้อไหน (ฉบับร่างที่พิมพ์ไว้ไม่หาย)

## 3. การส่งคำตอบ: รอผลยืนยันก่อนถือว่าเสร็จ

- สถานะการส่งคือ pending → submitting → resolved โดยจะ resolved ก็ต่อเมื่อ
  **RPC ตอบรับ (ack) แล้ว หรือมี settled event ที่เชื่อถือได้จาก agent มาถึงก่อน** —
  ฝั่งไหนมาถึงก่อนก็ใช้ฝั่งนั้น อีกฝั่งที่มาช้ารายงาน superseded โดยไม่วาดซ้ำ
  ([sessions.js](https://github.com/aukkwat83/muse-desktop-guix/blob/v1.1.33/src/server/sessions.js)
  `submitInteraction/_landSubmission/_failSubmission`)
- agent ปฏิเสธคำตอบ: การ์ดเดิมยังแก้ไขได้ ฉบับร่างไม่หาย ปุ่ม retry
  ใช้ UUIDv7 `commandId` เดิมและแสดงข้อผิดพลาดที่บอกทางแก้
- ส่งซ้ำคำตอบเดิม (รวมกรณี response หายกลางทาง): ได้ 200-duplicate ไม่ยิง RPC ซ้ำ;
  ส่งคำตอบขัดกันทับของเดิม: ได้ 409; ส่งถึงคำถามที่หายไปแล้ว: 404 พร้อมข้อความไทย
- approval หลายขั้น: ผล `terminal:false` คือขั้นต่อไปยังค้างอยู่ ระบบเก็บ accept
  ของขั้นนั้นไว้ให้ retry เดิม replay ได้โดยไม่ยิง RPC ซ้ำ ส่วนการตัดสินใจขั้นใหม่
  ใช้ command ใหม่ และ token `requirementId` กันตัดสินใจผิดขั้น (409 STAGE_STALE)
- การยกเลิกที่ agent รับทราบแต่เมิน จะถูกติดตามจนกว่าพรอมต์จะหายจริง
  ถ้ายังค้างจะ escalate ผ่านเส้นทาง settleTurn/watchdog เดิม —
  ไม่มีการแสดงว่า "ตอบแล้ว" ทั้งที่ agent ยังรอ
- ผู้ชนะการตัดสินใจอ้างจาก `decidedByCommandId`: ตรงกับ command ของเราเท่านั้น
  จึงจะป้าย choice ของเรา (ต่าง command/ไม่รู้ = null) ส่วน outcome แยกเดินทางของมันเอง

## 4. ฉบับร่างและโฟกัส

- ฉบับร่างคำตอบเก็บใน `sessionStorage` (มี memory fallback ถ้าใช้ storage ไม่ได้):
  รอดการปิด/เปิดกล่องใหม่ การสลับแชท การ retry และการ reload
  **ภายใน window session เดียวกัน** — ปิดแอปแล้วเปิดใหม่ฉบับร่างไม่อยู่
- ฉบับร่าง composer (ข้อความที่พิมพ์ค้างไว้ยังไม่ส่ง) ก็ใช้ `sessionStorage` เช่นกัน
- ป๊อปอัปที่เปิดอัตโนมัติไม่ย้ายโฟกัสออกจากช่องพิมพ์ที่กำลังใช้
  ปิดกล่องแล้วโฟกัสกลับที่เดิมอย่างปลอดภัย
- ฟอร์มล็อกขณะกำลังส่ง (กันพิมพ์หลุดนอก POST) และสัญญาณ "ผู้ใช้เห็นแล้ว"
  (`userInput/engaged`) ส่งเฉพาะเมื่อมีสัญญาณจริง — พิมพ์ โฟกัส เลือก
  หรือเปิดกล่องเอง — ไม่ใช่แค่ render การ์ดผ่านจอ
- ไม่มีปุ่มลัดตัวเลข/Esc ที่จะไปตอบคำถามผิดแชท หรือไปกวนช่องกรอกข้อความ

## 5. การแจ้งเตือนบน Linux: host เป็นผู้ส่ง แตะแล้วตรงคำถาม

- บน Linux host process (Node) เป็นผู้ส่งแบนเนอร์เองผ่าน typed GAction
  `notify-question (op, key)` ทาง `gdbus call` (ส่งเป็น argv ล้วน ไม่มี shell)
  เนื้อข้อความยาวไปทางไฟล์ JSON ใต้ runtime dir (UTF-8 ปลอดภัย)
  ([notify.js](https://github.com/aukkwat83/muse-desktop-guix/blob/v1.1.33/src/server/notify.js))
- การ์ดคำถามในเพจพก `hostNotified` มาด้วย: ถ้า host รับแจ้งเตือนไปแล้ว
  renderer จะไม่แบนเนอร์ซ้ำ และ shell ใช้ id เดียวกัน (`muse-q-<key>`) —
  คำถามเดียวคือแบนเนอร์เดียว ไม่ว่าฝ่ายไหนแสดง
- แตะแบนเนอร์แล้ว route ถึงแชท+คำถามตรงตัว: shell คิว route ไว้จนเพจพร้อม
  (รวมกรณี reload) มี handshake `ready` หลัง hydration และ receipt ต่อ tap;
  การเปิดจาก .service/DBus activation รองรับ shell ที่ปิดอยู่
- รายงานตามจริง: receipt `queued` หมายถึงอยู่ในคิว async ฝั่ง host
  (ยังไม่ถึง bus) ส่วน `accepted` หมายถึง bus รับเรื่องแล้ว —
  **ทั้งสองอย่างไม่ใช่การันตีว่าแบนเนอร์ขึ้นจอ** การแสดงผลจริงเป็น best-effort
  ตามการตั้งค่า OS (Do Not Disturb, กฎศูนย์แจ้งเตือน ฯลฯ) ผล accepted/FAILED
  ลง host log ทุกครั้ง (`MUSE_DESKTOP_NOTIFY=off` ปิดได้,
  `MUSE_DESKTOP_NOTIFY_LOG` ส่งลงไฟล์สำหรับ E2E)
- shell C/Python ลงทะเบียน action ที่ startup ใช้หน้าต่างเดียว ตรวจ same-origin
  ก่อน eval ทุกครั้ง; installer เหลือ entry ที่เห็นในรายการเดียว
  (canonical app-id + legacy ซ่อน NoDisplay + ไฟล์ .service)
- macOS คงเส้นทาง renderer → `/api/notify` เดิม ไม่เปลี่ยน

## 6. การกู้คืนหลัง reconnect และการรอ

- snapshot ฝั่งเซิร์ฟเวอร์เป็น authoritative: การ์ดที่ตอบไปแล้วแต่หายจาก snapshot
  จะถูกถอนออก ไม่ค้างเป็น pending ปลอม; tombstone ต่อแชทกัน GET ช้าฟื้นการ์ดเก่า
  และ revision/generation กัน SSE ใหม่โดนภาพเก่าป้ายทับ
- reconnect แล้ว submit state (กำลังส่ง/ผิดพลาด) กลับมาตรง ไม่ค้างบล็อกฟอร์ม
- ไม่มีการยกเลิกคำถามเงียบหลัง 5 นาที: ค่าเริ่มต้นคือรอผู้ใช้
  ผล timeout จริง (ถ้ามี) จะแสดงตามจริง ไม่แสดงว่าตอบแล้ว
